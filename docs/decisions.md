### 2026-11-17 캘린더 UI는 FullCalendar 사용

- 결정: 주간 캘린더 격자·일정 배치·겹침·드래그는 FullCalendar(v7)에 맡긴다. 직접 만든 격자 뼈대는 교체한다
- 이유: 격자와 드래그는 DayFit의 차별점이 아니다. 시간을 AI 에이전트 루프와 변경안 미리보기에 쓰기 위해
- 고려한 다른 방법: 직접 구현(시간 대비 얻는 게 적음), react-big-calendar(스타일 작업이 더 많음)
- 배운 점: 시간은 시간대를 명시해 저장하고(+09:00 또는 Z), 화면에서만 한국 시간으로 바꾼다

### 2026-11-17 상태 라이브러리 zustand 사용

- 결정 : 캘린더, 재배치 패널, 주간 요약이 같은 일정 목록을 봐야 하니 전역 상태가 필요
- 이유: context가 아니라 zustand를 선택한 이유는 context는 값이 바뀌면 컴포넌트가 다 다시 그려지지만 zustand는 필요한 값만 골라서 구독 가능하기 때문

### 2026-11-17 캘린더에서 진행 못한 계획에 대해서

- 결정 : 계획(못함) 판단은 하루 단위. 지난 일정은 자동으로 상태를 바꾸지 않고 "확인 필요"로 계산만 하고, 사용자가 답한 것만 저장한다.
  -> 앱 열면 "어제 확인 할 일정 3건" 출력 (체크를 못했거나, 안한 일정)
  -> 일정마다 했음, 못했음을 체크
  -> 못했음이 있으면 "못한 0건을 재배치 할까요" 확인 팝업
  -> 사용자 클릭시 ai가 변경안 제공
- 이유 : 잘못된 상태 저장과 잦은 알림 방지

### 2026-11-17 ai의 변경안이 3가지 일때 하나라도 저장 실패시 all or nothing

- 결정 : 변경안 중 하나라도 저장 실패시 모든 변경안은 적용하지 않는다
- 이유 : 사용자는 변경안에 대해 적용을 눌렀는데 1가지만 성공 나머지 실패시 일정이 꼬인다,

### 2026-11-17 변경안 승인 후 재배치된 계획을 되돌리기를 한다에 대한 생각

- 결정 : 재배치 일정에 별도로 되돌리기는 두지 않는다
- 이유 : 시간은 이미 지나서 되돌릴 의미가 없고, 수정이나 삭제로 충분하다고 판단

### 2026-11-17 일정 삭제 규칙

- 결정 : 일반 일정은 삭제 시 영구 삭제, 재배치한 일정 (미룬 계획)은 삭제시 영구삭제 or 보관함 롤백

### 2026-11-18 개발 방식: 테크 리드 + AI 구현

- 결정 : 나는 설계·검증·의사결정(테크 리드)을 맡고, 구현은 AI에게 맡긴다. 단 에이전트 루프는 흐름을 내가 직접 쓰고 AI가 코드로 옮긴다
- 이유 : 4주 안에 핵심 기능(문장 추가 → AI 재배치 → 승인)까지 완성하는 게 목표다. 직접 타이핑하는 시간보다, 규칙을 정하고 결과를 검증하고 설명할 수 있는 능력이 더 중요하다고 판단
- 지키는 것 : 기능마다 확인 기준을 먼저 정하고, 끝나면 안 보고 세 문장으로 설명한다. 에러는 원인을 먼저 파악하고 기록한다

### 2026-11-18 카테고리는 뒤로 미룸

- 결정 : 카테고리 기능(데이터, 화면 표시, 관리)은 핵심 기능이 끝난 뒤에 다시 판단한다. 데이터 구조의 categoryId는 남겨두고 지금은 항상 null
- 이유 : 핵심(문장 추가 → AI 재배치 → 승인)에 꼭 필요하지 않다. 블록 색은 상태(완료·못 함·미룸)로 구분하기로 해서, 카테고리 색까지 쓰면 색의 의미가 겹친다
- 다시 볼 시점 : 통계 기능(요구사항 5번)을 만들 때

### 2026-11-18 미루기는 AI 재배치의 결과, 팝업의 미루기는 보조

- 결정 : 메인 흐름은 "전날 못 한 일을 모아 → 오늘 AI가 재배치 변경안 제안 → 승인"이다. 승인하면 내부적으로 postpone이 실행된다. 일정 팝업의 미루기 버튼은 AI 없이 직접 옮기고 싶을 때 쓰는 보조 기능으로 둔다
- 이유 : 사용자는 못 한 일정을 직접 "미루기"하기보다 끌어서 옮기거나 그냥 내버려둔다. DayFit은 "못 했어요"라고 답만 하면 AI가 대신 미뤄주는 게 구글 캘린더보다 나은 점이어야 한다

### 2026-11-19 변경안은 추가와 미루기만, 삭제는 AI가 제안하지 않는다

- 결정 : 변경안(ProposedChange)의 종류는 추가(add)와 미루기(move) 두 가지다. 미루기는 승인하면 postpone으로 실행된다
- 이유 : 삭제는 되돌리기가 없고, 일정을 지우는 판단은 사용자가 팝업에서 직접 하는 게 안전하다. AI가 틀려도 잃는 일정이 없다
- 다시 볼 시점 : 진짜 AI로 교체하고 "취소해줘" 같은 요청이 필요해질 때

### 2026-11-19 변경안 승인 방식: 전체 검증 후 set 한 번

- 결정 : 승인하면 변경안 전체를 먼저 검증한다(대상 존재, done·postponed 아님, 시간 순서, 중복 미루기). 하나라도 안 되면 일정은 하나도 바뀌지 않고 이유만 보여준다. 통과하면 set 한 번으로 반영한다
- 이유 : 11-17 all or nothing 결정을 지금 구조(메모리 스토어)에서 지키는 방법. "저장 실패"의 의미는 저장소가 Supabase로 바뀔 때 다시 정한다
- 구현 : 미루기 규칙을 postponeInList 한 곳에 두고 스토어의 postpone과 변경안 적용이 같이 쓴다

### 2026-11-19 일정이 겹쳐도 허용하고 변경안 팝업에 경고만 표시

- 결정 : 변경안이 기존 일정이나 다른 변경과 겹쳐도 승인을 막지 않는다. 팝업에 경고를 보여준다
- 이유 : 캘린더(FullCalendar)가 겹침을 배치해 주고, 사용자가 의도해서 겹치는 경우도 있다. 막으면 사용성이 떨어진다

### 2026-11-19 변경안 상태는 별도 스토어(proposalStore)에 둔다

- 결정 : 승인 대기 중인 변경안은 zustand proposalStore에 하나만 둔다. 승인 전에는 일정 스토어를 건드리지 않는다
- 이유 : 변경안을 올리는 곳(헤더의 지난 일정 확인 팝업)과 보여주는 곳(본문의 ChangePreview)이 서로 다른 컴포넌트 트리라 props로 연결할 수 없다
- 고려한 다른 방법 : CalendarApp이 상태를 갖는 방식은 헤더의 DailyCheck가 닿지 못해서 제외

### 2026-11-19 가짜 해석기는 최소로, 재배치도 같은 파일에

- 결정 : 가짜 재배치(못 한 일을 오늘 지금 이후 빈 시간에 순서대로)는 parseEvent.ts 안에 두고, 월요일 진짜 AI 교체 때 이 파일 안쪽만 바꾼다. 변경안 형식(schema)과 API의 zod 검증, 화면은 그대로 둔다
- 이유 : 일회용 코드를 늘리지 않고, AI 호출은 한 파일에만 둔다는 원칙 유지

### 2026-11-19 변경안의 미루기 대상은 missed(못 했다고 답한 일정)만

- 결정 : 변경안의 미루기(move)는 상태가 missed인 일정만 대상으로 한다. 답하지 않은 planned, 끝낸 done, 이미 미룬 postponed는 검증에서 전체 거부한다
- 이유 : 11-17 결정(지난 일정은 사용자가 답한 것만 저장)과 같은 맥락. 사용자가 "못 했어요"라고 답하지 않은 일정을 AI가 마음대로 옮기면 안 된다. 진짜 AI가 실수로 멀쩡한 일정을 옮겨도 검증이 막아준다
- 다시 볼 시점 : "OO을 금요일로 미뤄줘" 같은 문장 이동 요청을 붙일 때

### 2026-11-19 문장 추가는 변경안으로 감싸지 않는다

- 결정 : 변경안은 AI가 기존 일정을 옮기자고 제안하는 재배치 흐름 전용이다. 문장으로 일정을 추가하는 건 원래대로 "해석 → QuickAdd 안의 미리보기 → 캘린더에 추가(addEvent)"로 둔다
- 이유 : 추가는 바꿀 기존 일정이 없고 사용자가 쓴 문장을 그대로 해석한 결과라 "변경안"이 아니다. 1건짜리에는 all or nothing도 의미가 없다. 팝업·검증을 재활용하려고 감쌌던 건 구현 편의였고, 개념을 흐렸다
- 남겨둔 것 : 스키마와 검증의 add 타입은 지금 쓰는 곳이 없다. 재배치에서 새 일정을 함께 제안할 일이 생기지 않으면 지울 후보
