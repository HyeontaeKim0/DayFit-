### 2026-11-17 Next.js App Router로 시작

- 결정: Next.js(App Router) + TypeScript strict로 프로젝트를 시작한다.
- 이유: LLM API 키를 서버에서만 다뤄야 하고, 스트리밍 응답을 서버 라우트에서 바로 내려줄 수 있다.
- 고려한 다른 방법: Vite + 별도 백엔드 (서버를 따로 운영해야 해서 범위가 커짐)

### 2026-11-17 카테고리를 별도 데이터로 분리

- 결정: 카테고리를 일정과 분리해서 이름·색상과 함께 저장하고, 일정은 categoryId로 참조한다
- 이유: 캘린더에 카테고리별 색을 보여주고, "이번 주 공부 몇 시간?" 같은 통계가 표기 차이로 나뉘지 않게 하기 위해
- 고려한 다른 방법: 고정 목록(자유도 부족), velog 태그식 자유 입력(색상 저장과 통계 일관성 문제)

### 2026-11-17 일정 상태 4가지와 미루기 기록

- 결정: planned / done / missed / postponed. 미룰 때 원래 일정을 지우지 않고 postponed로 남긴다
- 이유: 못 한 일(missed)을 AI 재배치 대상으로 구분하고, 몇 번 미뤘는지도 기록으로 남기기 위해

### 2026-11-17 AI 사용하여 디자인 시안 도출

- 결정 : AI로 시안을 빠르게 뽑고, 직접 정한 기준으로 수정 예정
- 이유 : 우선 화면 스케치 용도로 뽑은것이고, 디자인은 3주차에 다듬기로 함, 지금은 와이어 프레임 용도

### 2026-11-17 캘린더 UI는 FullCalendar 사용

- 결정: 주간 캘린더 격자·일정 배치·겹침·드래그는 FullCalendar(v7)에 맡긴다. 직접 만든 격자 뼈대는 교체한다
- 이유: 격자와 드래그는 DayFit의 차별점이 아니다. 시간을 AI 에이전트 루프와 변경안 미리보기에 쓰기 위해
- 고려한 다른 방법: 직접 구현(시간 대비 얻는 게 적음), react-big-calendar(스타일 작업이 더 많음)
- 배운 점: 시간은 시간대를 명시해 저장하고(+09:00 또는 Z), 화면에서만 한국 시간으로 바꾼다

### 2026-11-17 상태 라이브러리 zustand 사용

- 결정 : 캘린더, 재배치 패널, 주간 요약이 같은 일정 목록을 봐야 하니 전역 상태가 필요
- 이유: context가 아니라 zustand를 선택한 이유는 context는 값이 바뀌면 컴포넌트가 다 다시 그려지지만 zustand는 필요한 값만 골라서 구독 가능하기 때문

### 2026-11-17 캘린더에서 진행 못한 계획에 대해서

- 결정 : 계획(못함) 판단은 하루 단위. 지난 일정은 자동으로 상태를 바꾸지 않고 "확인 필요"로 계산만 하고, 사용자가 답한 것만 저장한다.
  -> 앱 열면 "어제 확인 할 일정 3건" 출력 (체크를 못했거나, 안한 일정)
  -> 일정마다 했음, 못했음을 체크
  -> 못했음이 있으면 "못한 0건을 재배치 할까요" 확인 팝업
  -> 사용자 클릭시 ai가 변경안 제공
- 이유 : 잘못된 상태 저장과 잦은 알림 방지

### 2026-11-17 ai의 변경안이 3가지 일때 하나라도 저장 실패시 all or nothing

- 결정 : 변경안 중 하나라도 저장 실패시 모든 변경안은 적용하지 않는다
- 이유 : 사용자는 변경안에 대해 적용을 눌렀는데 1가지만 성공 나머지 실패시 일정이 꼬인다,

### 2026-11-17 변경안 승인 후 재배치된 계획을 되돌리기를 한다에 대한 생각

- 결정 : 재배치 일정에 별도로 되돌리기는 두지 않는다
- 이유 : 시간은 이미 지나서 되돌릴 의미가 없고, 수정이나 삭제로 충분하다고 판단

### 2026-11-17 일정 삭제 규칙

- 결정 : 일반 일정은 삭제 시 영구 삭제, 재배치한 일정 (미룬 계획)은 삭제시 영구삭제 or 보관함 롤백
